# PushUp Trainer — общие ViewModel и логика presentation

## 1. Область действия и архитектура

Это проектный стандарт PushUp Trainer для общей presentation-логики Android и iOS. ViewModel, `UiState`, `UiEvent` и преобразования в UI-модели находятся в `shared/src/commonMain`, когда их зависимости доступны на обеих платформах.

Применяй вместе с соседними `pushup-trainer-ui` и `pushup-trainer-di`. Для переходов и entry scope применяй `pushup-trainer-navigation`: выбран Navigation 3. Правила UI kit, Preview и DI остаются в соответствующих skills и не заменяются этим документом.

Используется облегчённый однонаправленный поток:

```text
Screen → UiEvent → ViewModel.onEvent
                    ├── UseCase → результат/Flow → UI mapper → UiState
                    └── Router → навигационный корень Navigation 3
UiState → Root → Screen
```

Отдельные обязательные Reducer, Store, Mutation, ActionDispatcher и BaseViewModel не требуются. Сохраняй реальные имена `state`/`uiState`, Root/Route и существующие экраны, не переписывай их ради совпадения с примером.

## 2. Границы задачи и существующие контракты

- Перед изменением прочитай целиком соответствующие `UiState`, `UiEvent`, Screen, runtime Root/Route, Preview, DI и маршруты. Проследи существующие действия пользователя до обработчиков.
- Найди фактические domain-контракты и типы результатов. ViewModel зависит от UseCase; не вызывай из неё DAO, Room, data source, Ktor или платформенную камеру напрямую.
- Платформенные ресурсы доступны через общие контракты существующей ML/интеграционной области. Не создавай общий интерфейс, который всё равно принимает Android Context, Activity или iOS framework-классы.
- Новые UseCase/Repository/контракты допустимы, когда они нужны согласованной задаче и создание соответствующего слоя входит в её объём. Общего запрета на их разработку в PushUp Trainer нет.
- Если задача ограничена подключением готовой логики, а нужного контракта нет, укажи конкретный пробел и продолжай независимые части. Согласуй расширение объёма; не изображай успешное сохранение и не подменяй API вымышленным методом.
- В UI-only задаче допустим явно оговорённый каркас ViewModel. `Unit` в отложенном обработчике такого каркаса не выдаётся за готовый сценарий и не считается автоматически дефектом вне его объёма.

Сценарии аудитов, авторизации аудитора и административные ограничения Food Audit не относятся к этому проекту. Наличие маршрута или скриншота не разрешает самовольно добавлять бизнес-функциональность.

## 3. Одно основное состояние экрана

Наружу предоставляй read-only `StateFlow`, изменяемое состояние оставляй приватным:

```kotlin
private val _state = MutableStateFlow<TrainingResultUiState>(TrainingResultUiState.Loading)
val state: StateFlow<TrainingResultUiState> = _state.asStateFlow()
```

Это пример формы на существующем типе проекта, а не указание начинать каждый экран с `Loading`.

- Все связанные факты экрана хранятся в одном основном иммутабельном `UiState`: режим, цель, счётчик, доступность действий, loading/error и видимость экранных подсказок.
- Для взаимоисключающих вариантов используй подходящие sealed-типы или enum, а не независимые флаги, допускающие бессмысленные сочетания.
- Не создавай отдельные mutable-потоки для тех же режима, счётчика или ошибок, уже представленных в `UiState`. Производный Flow без второго хранилища допустим.
- Обновляй состояние атомарно через `_state.update { current -> current.copy(...) }`. Не меняй опубликованные списки и вложенные объекты на месте.
- Лямбда `update` может быть выполнена повторно. Вызов UseCase, навигация, сохранение, управление камерой и другие побочные действия выполняются снаружи неё.
- Новая эмиссия источника не должна без причины сбрасывать независимые выбор пользователя, ввод или выбранную дату. Сопоставляй обновляемые элементы по устойчивому ID.
- Domain/data модели, DAO, ресурсы камеры и экземпляры анализатора не помещаются в `UiState`. Преобразование в UI-модели происходит за пределами Composable.

Единый основной `UiState` не означает, что видеокадры и все промежуточные данные ML должны проходить через него. Границы высокочастотных данных описаны ниже.

## 4. События пользователя и внешние данные

Единственная публичная точка входа **действий из UI** — `onEvent(event)`. Внутри используй исчерпывающий `when` и приватные обработчики по ответственности.

- Screen передаёт `UiEvent`, вложенные компоненты — узкие callbacks. Не вызывай отдельные `viewModel.save()`, `start()` или `setMode()` из разных кнопок.
- Подписки на repository/ML Flow, таймеры и внешние callbacks не являются действиями пользователя. Не превращай их в `UiEvent.FrameReceived`, `DataLoaded` или аналогичный искусственный поток.
- Нужные lifecycle-сигналы подключаются через существующую интеграцию/владельца ресурсов. Не маскируй уход приложения в фон под пользовательское нажатие и не создавай второй публичный API кнопок.
- Сохраняй все действия уже принятого UI: смену режима, цель, подсказки, выбранную дату, тему, Back и навигацию в пределах задачи. Удаление существующего события требует реальной причины, а не удобства переписывания ViewModel.

## 5. Root, Screen, Koin и Navigation 3

Runtime Root/Route получает ViewModel через общий поддерживаемый Koin API, собирает состояние lifecycle-aware и передаёт его в Screen. Пример формы границы:

```kotlin
@Composable
fun TrainingResultRoute(
    viewModel: TrainingResultViewModel = koinViewModel(),
) {
    val state by viewModel.state.collectAsStateWithLifecycle()
    TrainingResultScreen(
        state = state,
        onEvent = viewModel::onEvent,
    )
}
```

При интеграции используй реальные сигнатуры и существующее имя runtime-компонента. Этот пример не разрешает создавать второй Root рядом с уже существующим Route.

- Screen и Preview не получают ViewModel, Router, back stack, репозиторий или реальные аппаратные зависимости.
- ViewModel регистрируется через классический `viewModel { ... }` в модуле своей фичи; зависимости передаются конструктором. Не используй скрытый `getKoin()`/GlobalContext и не запускай Koin повторно.
- Используй существующие DI-агрегаторы и `includes(...)`; не добавляй пустую иерархию ради образца.
- Runtime Root создаётся в контексте своей Nav3 entry. Проверь entry-scoped ViewModelStore: ViewModel не должна случайно жить в Activity scope или разделяться между независимыми entry.
- Аргументы Nav3 передаются из типизированного ключа в Root/ViewModel явно через поддерживаемую фабрику/Koin параметры. Не предполагай работу `SavedStateHandle.toRoute()` из Navigation 2.
- `SavedStateHandle` может хранить подходящий небольшой ввод/идентификатор, но не заменяет repository и не сохраняет видеопоток, камеру или анализатор.

Общий код использует `androidx.lifecycle.ViewModel` из multiplatform-зависимости. Класс с таким package name сам по себе не делает ViewModel Android-only. Android Context, `R.string` и UIKit-классы в общий код не переносятся; сообщения представляются принятой UI-моделью и общими ресурсами.

## 6. Flow и корутины

До подключения Flow выясни: холодный он или горячий, запускает ли подписка источник, кто собирает данные и кто останавливает источник, как устроены retry и повторное подключение.

- Долгоживущий `collect` обычно не завершается. Не ставь после него запуск тренировки, refresh или сохранение, которые должны выполняться во время наблюдения. Независимое наблюдение и отдельную операцию запускай независимыми дочерними задачами либо эквивалентной проверенной композицией Flow.
- `first()` подходит для осознанного разового чтения, но не заменяет непрерывное наблюдение за тренировкой или историей.
- Второй коллектор холодного Flow может повторно запустить upstream. Не запускай два экземпляра камеры/анализа или два сохранения из-за случайного дублирования подписки.
- Не запускай обновление источника при каждой его же эмиссии. Избегай цикла «запись → наблюдение → запись».
- `collectLatest` отменяет обработку предыдущей эмиссии. Используй его для отменяемой подготовки отображения, а не для обязательного сохранения или последовательного подсчёта повторений.
- Операторы `map`, `catch`, `filter` не запускают холодный Flow без collection. `catch` не означает автоматический restart после завершения потока с ошибкой.
- Не используй `GlobalScope`, `runBlocking` во ViewModel, бесконтрольные собственные CoroutineScope или `Dispatchers.IO` на все операции. Блокирующая работа получает контекст в соответствующем нижнем слое.
- `Job` для управления жизнью задачи не является вторым источником экранных данных. Явно предотвращай повторный запуск уже активного наблюдения.

## 7. Ошибки, отмена и повторные действия

- Различай начальную загрузку, обновление поверх существующих данных и сохранение. Ошибка одной операции не должна стирать уже показанные результаты или пользовательский ввод.
- Разбирай реальный контракт результата UseCase: исключение, Result или доменный тип. Не считай отсутствие исключения доказательством успеха, если результат содержит отказ.
- При перехвате исключений пробрасывай `CancellationException`. Бездумный `runCatching` тоже может её перехватить. Отмена не превращается в UI-ошибку, успешную запись или навигацию.
- Завершай loading/saving корректно для каждого исхода, включая отмену. Очистка ресурсов выполняется и при отмене; при необходимости приостанавливаемой очистки используй узкую гарантированную секцию, а не неотменяемую бизнес-операцию целиком.
- Защита от двойного нажатия должна работать в обработчике/контракте операции. Одного disabled-состояния кнопки или debounce недостаточно для гарантии единственного сохранения.
- В retry сохраняй относящиеся к той же операции данные и идентификатор. Не запускай заново тренировку для повторной попытки сохранить уже полученный итог.

## 8. ML, кадры и состояние интерфейса

Разделяй обработку позы и отображение:

```text
Платформенная камера → PoseSource/существующая интеграция → анализатор
  → подготовленный результат тренировки → ViewModel → UI-модели/UiState
```

- Захват кадров, нормализация координат, модель ML и решение «засчитать повторение» принадлежат соответствующей ML/domain/integration области, а не Composable и не алгоритмам внутри ViewModel.
- Не копируй сырые кадры и все промежуточные координаты в общий экранный `UiState` на каждом кадре. Основное состояние содержит нужный пользователю результат: счётчик, режим, состояние тренировки, подсказку, доступность действий.
- Если UI действительно рисует скелет/overlay, ему нужны соответствующие подготовленные UI-данные. Допустим отдельно обоснованный поток или область состояния этого компонента без дублирования основного состояния и domain-моделей в UI. Не запрещай нужные обновления только из-за их частоты.
- Ограничивай частоту и область чтения данных **для отображения**, когда это нужно. Не теряй входные данные анализа/повторения ради уменьшения recomposition и не ставь произвольный `sample` перед алгоритмом подсчёта.
- Внешние ML-эмиссии обрабатываются подпиской/контрактом, а не проходят через пользовательский `onEvent`.
- После остановки/нового запуска запоздавший callback прежней сессии не должен менять новый счётчик или уже зафиксированный итог. Проверяй принадлежность результата активной сессии и допустимую фазу обработки.

## 9. Владение камерой и жизненный цикл

До реализации назначь одного владельца запуска, остановки и освобождения камеры/ML. ViewModel управляет сценарием через общие контракты; реальная привязка аппаратного ресурса к платформенному view/lifecycle остаётся в интеграционном слое.

- Первая эмиссия `UiState`, обычная recomposition и повторное подключение Root не должны каждый раз запускать новую тренировку.
- Для `start → stop → start` проверь новый рабочий источник и отсутствие старых подписок/callbacks. Нельзя повторно использовать уже закрытый ресурс, если его контракт этого не позволяет.
- Потеря видимости экрана, background, удаление Nav3 entry и очистка ViewModel — разные события. Приостановка `collectAsStateWithLifecycle` сама по себе не останавливает камеру и работу ViewModel.
- Для фонового перехода зафиксируй согласованную политику паузы/остановки, сохранения промежуточного состояния и resume. Не выдумывай автоматическое завершение или продолжение захвата в фоне.
- Проверь освобождение аппаратных ресурсов при навигации, ошибке и отмене. Если entry остаётся в back stack, одной очистки ViewModel недостаточно.
- При восстановлении после завершения процесса поднимай допустимые данные через принятый механизм. Живой анализатор и кадры не восстанавливаются из saved state; камера запускается заново только по разрешённому сценарию и с учётом разрешений/готовности платформенного view.

## 10. Завершение, сохранение и переход к результату

Когда задача включает реальное завершение тренировки, обеспечь согласованный порядок:

1. Прими завершение текущей сессии однократно; повторный клик, автоматическое достижение цели и системный Back не должны запустить конкурирующие завершения.
2. Останови/заверши обработку по реальному контракту владельца сессии. Учитывай уже выполняющиеся callbacks и зафиксируй неизменяемый итог ровно этой сессии. Простого вызова `stop()` недостаточно, если он асинхронный.
3. Сохрани итог через фактический UseCase и устойчивый идентификатор. Число повторений, цель, длительность, время и ошибки должны относиться к одной сессии; согласованную атомарность обеспечивает domain/data.
4. Обработай подтверждённый успех либо ошибку. При ошибке сохрани итог для retry, не показывай «Тренировка сохранена» и не открывай успешный результат.
5. После успеха отправь Router команду с идентификатором сохранённой тренировки и согласованной политикой стека. Перед применением команда должна оставаться актуальной для своей entry/сессии.

При отмене/сбое после фактической записи, но до навигации, запись могла уже сохраниться. Повторное открытие/попытка должны проверять тот же ID и состояние хранения, а не создавать вторую тренировку. UI-флаг не даёт гарантии идемпотентности после пересоздания процесса.

Промежуточный UI результата до завершения сохранения допустим только по согласованному UX. Он явно отличается от подтверждённого «сохранено» и не запускает повторное сохранение при повторном показе экрана.

Серия дней, рекорд, календарь и среднее вычисляются по согласованным domain-правилам. ViewModel не должна самовольно решать, считается ли нулевая тренировка, какой часовой пояс использовать или к какому дню отнести тренировку через полночь.

## 11. Навигация и одноразовые действия

Навигация идёт через общий Router по `pushup-trainer-navigation`; ViewModel не получает NavController, NavDisplay или изменяемый back stack.

Команда перехода не хранится как переигрываемый флаг `isSuccess/goToResult` в `UiState`. Состояние «данные сохранены» может быть фактом UI, но его повторный показ не должен автоматически повторять команду перехода. Для иных UI-эффектов используй существующий механизм, не создавая второй router/event bus без необходимости.

Отправка в Channel не доказывает применение навигации. Обрабатывай недоступность/переполнение и устаревание команды согласно контракту Router. После пересоздания решение о результате основывается на сохранённой сессии и новой проверке сценария, а не на replay старой очереди.

## 12. Проверка реализованного поведения

Используй имеющуюся тестовую инфраструктуру и управляемые fake-контракты. Выбирай проверки по реально реализованным сценариям:

- **Живой Flow:** источник остаётся активным; независимый старт/refresh выполняется; следующая эмиссия обновляет UI. Один `flowOf(...)` этого не доказывает.
- **Состояние:** новая эмиссия не сбрасывает независимый ввод/режим, UI-модели не мутируются на месте.
- **Сбой и отмена:** корректные loading/error; отмена пробрасывается; данные для retry сохраняются; ложного успеха нет.
- **Сессия:** старт, остановка, повторный старт; поздний callback старой сессии; ошибка запуска/камеры; освобождение ресурсов.
- **Завершение:** повторный клик и достижение цели дают одно завершение/сохранение/допустимый переход; итог не меняется после фиксации; retry не создаёт дубль.
- **Lifecycle:** background/resume, скрытая entry в стеке, удаление entry и восстановление host проверены отдельно по поддерживаемому сценарию.
- **DI и навигация:** ViewModel разрешается через реальные агрегаторы Koin, аргументы и entry scope корректны; Router получает правильный ID и только после нужного результата.
- **UI:** все исходные события сохранены; Preview работает без ViewModel и DI.

После изменения кода запусти доступную сборку и соответствующие тесты. В отчёте различай unit-проверки, реальное устройство и непроверенные платформы. Android-тесты не подтверждают запуск iOS; на Windows явно укажи ограничение. Изменение только SKILL.md не требует сборки приложения.
