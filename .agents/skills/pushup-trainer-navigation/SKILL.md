# PushUp Trainer — общая навигация на Navigation 3

## 1. Область действия и связанные правила

Это проектный стандарт PushUp Trainer. Общая навигация Android и iOS находится в `shared/src/commonMain`, как и общий Compose UI. Платформенные приложения предоставляют точки входа и необходимую платформенную интеграцию.

Для UI применяй `pushup-trainer-ui`, для регистраций — `pushup-trainer-di`, для реализации ViewModel — `pushup-trainer-viewmodel`. Эти skills находятся рядом, в `.agents/skills`. Данный документ дополняет их правилами навигации.

Выбран **Navigation 3**. Сохраняется архитектурный стиль: `UiEvent → ViewModel → Router → RouterController → стек → NavDisplay`. Не добавляй обязательные Store, Reducer или второй механизм навигационных эффектов.

Приоритет имеют явные требования пользователя и согласованный UX. Примеры ниже показывают устройство навигации, а не разрешают реализовывать дополнительные экраны или бизнес-сценарии. UI-only задача не включает подключение навигации.

## 2. Зависимости и платформы

- Перед интеграцией проверь актуальный version catalog, source sets и уже подключённые Navigation, Lifecycle, SavedState, Serialization и Koin. Не копируй номера версий из старых примеров.
- Для общего UI используй совместимый multiplatform-артефакт `org.jetbrains.androidx.navigation3:navigation3-ui`. Нужные Lifecycle/ViewModel-интеграции также должны поддерживать общий код и iOS.
- Kotlin Serialization и сериализуемые ключи нужны для восстановления маршрутов. Подключай только необходимые зависимости в рамках задачи.
- `NavHost`, `NavController`, `NavGraphBuilder`, `composable<Route>` и `SavedStateHandle.toRoute()` из Navigation 2 не являются основой выбранной архитектуры. Не переноси их из Food Audit и не подключай Navigation 2 параллельно.
- Android Activity, iOS UIViewController и платформенные API не должны попадать в общие маршруты, Router или ViewModel.

Navigation 3 управляется стеком, принадлежащим приложению. Поэтому запрет исходного Food Audit на собственное состояние стека нельзя переносить буквально: здесь собственный стек — часть выбранного API.

## 3. Владение кодом

Используй корневой пакет `com.example.pushuptrainer_mobile` и существующие имена проекта:

```text
shared/src/commonMain/kotlin/com/example/pushuptrainer_mobile/
├── core/navigation/           # Router, RouterController, команды, их DI
├── features/<feature>/
│   ├── navigation/            # маршрут и регистрация entry этой фичи
│   ├── presentation/          # Root/Route, Screen, UiState, UiEvent, ViewModel
│   └── di/                    # существующие регистрации фичи
└── ...                       # существующая точка сборки общего приложения
```

Это схема ответственности, не требование создать каждый показанный пакет. Сохраняй сложившееся расположение и названия. Существующий runtime-компонент с суффиксом `Route` не переименовывай в `Root` ради единообразия.

Фича владеет своим сериализуемым маршрутом, извлечением его аргументов и регистрацией content/entry. Общая точка сборки объединяет регистрации и отображает `NavDisplay`. Она не создаёт вручную все ViewModel и не содержит бизнес-логику всех экранов.

Не собирай все конкретные маршруты в один глобальный файл и не заводи отдельные Gradle-модули api/impl без задачи на модульность.

## 4. Единственный источник состояния стека

Для каждого реального навигационного корня назначь одного владельца стека. По умолчанию достаточно одного общего корня.

- Корень хранит восстанавливаемый back stack и передаёт его в `NavDisplay`.
- `RouterController` применяет команды к этому же экземпляру стека; он не хранит его вторую копию.
- Текущий маршрут, выбранная вкладка и возможность Back выводятся из фактического состояния навигации. Не поддерживай параллельное mutable-поле с той же информацией в ViewModel экрана.
- Применяй изменения стека последовательно в UI-контексте. Выполнение одной команды не должно приостанавливаться посередине изменения стека.
- `NavDisplay.onBack`, системный Back и жесты должны сходиться к одному правилу изменения стека. Не обрабатывай один Back двумя независимыми обработчиками.
- Последний элемент стека не удаляется обычным Back: поведение на корневом экране определяется платформой и согласованным UX.

При настоящих нескольких стеках, например отдельных историях вкладок, каждый стек имеет одного владельца. Активная вкладка, её стек и сохранённые стеки должны составлять согласованное состояние. Не создавай независимый стек для каждого экрана.

## 5. Маршруты и аргументы

Используй типизированные `@Serializable` ключи Navigation 3. Пример формы маршрута:

```kotlin
import androidx.navigation3.runtime.NavKey
import kotlinx.serialization.Serializable

// Этот тип объявляется в навигационном пакете фичи результата.
@Serializable
data class TrainingResultRoute(val workoutId: String) : NavKey
```

Правила:

- Для маршрута без аргументов подходит `@Serializable data object`, с аргументами — `@Serializable data class`.
- Передавай минимальные устойчивые параметры: идентификатор сохранённой тренировки, выбранный режим или цель, когда они действительно нужны сценарию.
- Room entity, UI-модели результата, ViewModel, кадры, изображения, анализатор и экземпляры камеры через маршруты не передаются.
- Сериализуемый ключ поступает в entry; оттуда передавай аргументы в feature Root/ViewModel явно через поддерживаемые Koin параметры или фабрику. Не предполагай автоматическое появление Nav3-аргументов в `SavedStateHandle` по правилам Navigation 2.
- У отсутствующей или удалённой тренировки должен быть определённый UI-результат. Нельзя подставлять демонстрационную тренировку или показывать ложный успех.
- Заранее определи, допустимы ли два одинаковых маршрута в стеке. Повторный клик обычно не должен создавать дубликат. Если нужны независимые экземпляры с одинаковыми аргументами, их сохраняемая идентичность и ViewModel scope должны различаться.

## 6. Router и RouterController

`Router` — интерфейс, через который feature ViewModel запрашивает переход. `RouterController` — управляющая сторона той же реализации: выдаёт команды единственному потребителю и связывается с владельцем стека.

Команды должны описывать операции с маршрутами и стеком, а не быть лямбдами `NavController.() -> Unit`. Добавляй операции только под реальные сценарии: открыть маршрут, вернуться, заменить текущий маршрут или перейти к существующему элементу стека.

Контракт обязан явно определять:

1. Что считается успешной отправкой команды: постановка в очередь или уже выполненный переход.
2. Кто применяет её и как проверяется актуальность отправителя/навигационного корня.
3. Как обрабатываются отсутствие потребителя, переполнение очереди и отмена.
4. Какие команды допустимы при background, повторном клике и смене корня.

Одна реализация может предоставляться в Koin под интерфейсами `Router` и `RouterController`; обе регистрации обязаны разрешаться в **один объект**. Сам экземпляр восстанавливаемого стека принадлежит корню, а не создаётся заново каждым потребителем Router.

Не вводи глобальный mutable singleton вне Koin, отдельный `StateFlow` намерений перехода или второй `UiEffect`-канал для тех же навигационных действий. Domain/data не знают Router и маршрутов.

## 7. Доставка команд и жизненный цикл

Для каналовой реализации используй ограниченную очередь и один потребитель команд в стабильном общем навигационном корне. `receiveAsFlow()` с несколькими коллекторами распределяет команды между ними; это не широковещательная доставка.

- Подключай и отключай контроллер вместе с его корнем. Обычная recomposition не создаёт второй контроллер, потребитель или привязку.
- В состоянии background стек не должен изменяться незаметно для пользователя. Сбор для применения команд должен учитывать lifecycle корня.
- Если очередь переживает background, перед применением команды после resume проверь, что исходные entry/сессия и нужный корень ещё актуальны. Политика ожидания или отклонения должна быть явной.
- При уничтожении/замене корня его отложенные команды должны инвалидироваться. Не применяй их автоматически к новому корню. Callback на уничтоженный root/контроллер освобождается при отсоединении.
- Если есть `tryEmit`, он возвращает результат отправки; вызывающая сторона обрабатывает отказ. `Channel.BUFFERED` не означает гарантированную доставку и не решает проблему устаревших команд.
- Канал сам по себе не даёт exactly-once между отменой потребителя и применением эффекта. Не обещай такую гарантию и не используй очередь как доказательство сохранения бизнес-результата.
- Переходы, зависящие от записи данных, отправляй после подтверждённого сохранения. Восстановление после смерти процесса основывается на сохранённых данных и состоянии навигации, а не на повторной отправке старой команды.

Не собирай команды через `collectAsState` и не устанавливай их коллектор внутри каждого Screen. Пауза UI-коллектора не останавливает автоматически камеру или работу ViewModel.

## 8. Восстановление Android и iOS

Используй поддерживаемое сохранение стека Navigation 3, а не только `remember { mutableStateListOf(...) }` или singleton в DI.

Для `rememberNavBackStack` в общем коде учитывай отсутствие JVM reflection на iOS: настрой `SavedStateConfiguration`/`SerializersModule` для **всех** используемых ключей либо поддерживаемый эквивалент с явным сериализатором. Не ограничивай регистрацию первым экраном.

Разделяй три разных механизма:

| Что восстанавливается | Владелец |
| --- | --- |
| Маршруты, аргументы, активный стек | Навигационный корень и его SavedState-интеграция |
| Ввод и состояние конкретной entry | Saveable state / SavedStateHandle, где они подходят |
| Сохранённая тренировка, прогресс сессии | Domain/data согласно задаче |

Сериализуемость маршрута не доказывает восстановление всего приложения после завершения процесса. На iOS отдельно проверь, что host действительно сохраняет и возвращает нужное состояние. Холодный запуск, пересоздание host и возврат из background — разные проверки.

Различай логический навигационный корень и его привязку к конкретному host. Пересоздание host само по себе не означает новый пользовательский сценарий. Если сохранение завершилось, а старая команда потеряла актуальность при пересоздании, восстановленная entry сверяет состояние сессии с data и принимает новое решение о переходе согласно UX. Старую команду не переигрывают и тренировку повторно не сохраняют.

Живые ресурсы камеры/ML из saved state не восстанавливаются. Решение о продолжении, паузе или завершении прерванной тренировки принимается по согласованному сценарию, без повторного сохранения или автоматического запуска камеры из конструктора маршрута.

## 9. ViewModel и состояние отдельной entry

При создании `NavDisplay` обеспечь сохранение Compose state и ViewModelStore на уровне entry. Для актуального API это, в частности, `rememberSaveableStateHolderNavEntryDecorator()` и `rememberViewModelStoreNavEntryDecorator()` из совместимых библиотек; проверь сигнатуры выбранной версии.

- Получай ViewModel внутри content соответствующей entry через поддерживаемый общий Koin API.
- ViewModel сохраняется, пока её entry остаётся в стеке, и очищается после удаления entry согласно механизму Navigation 3.
- Две независимые entry не должны случайно получать один Activity-scoped экземпляр ViewModel.
- Нахождение entry в стеке не означает видимость экрана. Камера не должна продолжать работать только потому, что ViewModel ещё не очищена. Управление ресурсами описывается в `pushup-trainer-viewmodel`.
- Не создавай новую ViewModel вручную в `App`, Screen или при каждом обновлении состояния.

Koin Navigation 3 DSL не обязателен: feature-owned entry provider и обычного ViewModel DI достаточно. Не подключай новый DSL по примеру из документации без проверки поддержки **текущей** версии Koin и KMP. Koin-модули агрегируются только через `includes(...)` по существующей структуре; дополнительные пустые уровни ради примера не создаются.

## 10. Root, Screen и Preview

Feature Root/существующий runtime Route:

- получает типизированные аргументы и entry-scoped ViewModel через Koin;
- собирает публичный `StateFlow` lifecycle-aware;
- передаёт в Screen подготовленные state и `viewModel::onEvent`;
- подключает только реально необходимую платформенную/lifecycle-интеграцию.

Screen и компоненты UI kit получают state/UI-модели и callbacks. Они не получают Router, изменяемый back stack или `NavDisplay` для выполнения переходов. Preview работает с тестовым `UiState`, без ViewModel, Koin и камеры.

Обычная подсказка внутри экрана управляется его `UiState` по UI skill. Не превращай каждую подсказку или локальный popup в отдельный маршрут.

## 11. UX тренировки, Back и вкладки

Перед реализацией составь таблицу реальных переходов: действие, исходный экран, результат, изменение стека, поведение Back. Учитывай отдельно Main, подготовку, тренировку, результат, Progress и About, **если они входят в задачу и уже существуют**.

Не выводи окончательную политику стека из одного макета. Например, замена Workout на Result может быть нужна, чтобы Back не открывал завершённую тренировку, но её нужно согласовать с реальным сценарием. Зафиксируй поведение также для «Начать новую тренировку», возврата на главный экран и повторного выбора вкладки.

- После завершения пользователь не должен случайно продолжить уже сохранённую сессию из старой entry.
- Выбор той же вкладки не должен бесконечно добавлять одинаковые экраны.
- При переключении вкладок сохраняй или сбрасывай вложенную историю согласно UX, а не по случайному порядку команд.
- Системный Back/жест во время активной тренировки должен учитывать согласованную остановку ресурсов, подтверждение и сохранение. Нельзя обходить этот сценарий независимым `removeLast()`.
- Возврат из background не равен новому старту тренировки.

## 12. Проверки и типичные ошибки

Для изменяемого поведения проверь подходящими тестами:

- команды Router изменяют нужный стек; тот же объект контроллера используется в DI и корне;
- один клик, двойной клик, Back, повторный выбор вкладки и завершение не создают лишние entry;
- ключи и аргументы сохраняются/восстанавливаются, в том числе на iOS без reflection;
- две entry имеют правильную идентичность и ViewModel scope; удаление entry освобождает её ресурсы;
- команда не применяется к чужому/уничтоженному корню, отказ отправки и отмена не изображают успех;
- фон, resume и восстановление не переигрывают старые переходы и сохранения;
- ошибка сохранения оставляет пользователя на корректном экране с доступным retry;
- существующие UI-модели и Preview остаются рабочими.

Типичные ошибки: Android-only импорт в общем Router; перенос `SavedStateHandle.toRoute()` из Nav2; два стека одной истории; дублирующие обработчики Back; Activity-scoped ViewModel для всех entry; пересоздание контроллера при recomposition; вечная очередь устаревших команд.

После изменения кода запусти доступную сборку и адресные тесты. Проверки Android не подтверждают работу iOS. На Windows явно укажи, какие iOS-проверки не выполнялись; просмотру исходников не приписывай результат запуска. Для правки только SKILL.md достаточно проверки документа и ссылок, сборка приложения не требуется.
